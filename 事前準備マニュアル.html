はじめに 1まず読む

GitHub Copilot とは何か

この演習で使う GitHub Copilot について、使ったことがない人向けに説明します。設定作業に入る前に読んでください。何をする道具なのかを分かったうえで触るのと、分からないまま触るのとでは、4週間後の到達点がまったく変わります。

読了目安 10分前提知識 不要提供元 GitHub（Microsoft傘下）

一言でいうと

あなたがコードを書いている横で、「次はこう書くのでは？」と予測して提案してくれる AI です。
エディタ（Visual Studio Code）に組み込んで使います。提案は薄いグレーの文字で表示され、Tab キーを押すと採用、Esc キーで却下。あなたが採用しない限り、コードは1文字も書き換わりません。

Copilot ＝「副操縦士」という意味です。この名前は本質を的確に表しています。副操縦士は操縦を手伝いますが、機長はあくまであなたです。どこへ飛ぶかを決めるのも、計器の値がおかしいと気づくのも、最終的な責任を負うのもあなたです。この演習の全体を通して、この関係を意識してください。

どういう仕組みで動いているのか

中身を厳密に知る必要はありませんが、大まかな仕組みを知っているかどうかで、使いこなせるかが決まります。

図1：コメントを書いてから提案が出るまでの流れ

図2：「文脈（コンテキスト）」として送られているもの。AI はこれらだけを手がかりに予測している

★ 図2から分かる、いちばん実用的なこと。AI に渡っているのは、この5つだけです。つまり「Copilot の性能」より「あなたの伝え方」で結果が決まります。コメントを丁寧に書く、変数名をきちんと付ける、関係ないファイルは閉じる──たったこれだけで提案の質は目に見えて変わります。
★ この図から読み取ってほしい2つのこと
1. 提案の質は「文脈」で決まる。コメントを丁寧に書く、変数名をきちんと付ける、関係ないファイルを閉じる。それだけで提案の質が目に見えて変わります。「Copilot が使えない」と言う人の大半は、文脈の与え方が雑なだけです。
2. Copilot は「考えて」いない。もっともらしい続きを確率的に予測しているだけです。だから、平気で間違えます。これは故障ではなく、仕組み上そういうものです。

4つの使い方

Copilot には大きく4つの使い方があります。第1回のハンズオンで全部試しますので、ここでは「そういうものがある」と分かれば十分です。暗記する必要はありません。

「ハンズオン」とは
hands-on ＝「手を動かす」という意味です。講義を聞いて終わりではなく、受講者全員がその場で自分のパソコンを操作して、実際に機能を試す形式の授業を指します。第1回の前半（およそ90分）がこれにあたります。
進め方は次のとおりです。教員が前で1つの操作を示す → 全員が同じ操作を自分の画面で再現する → できたことを確認して次へ進む、の繰り返しです。分からなくなったらその場で手を挙げてください。全員が同じ画面を出している前提で進むので、黙って置いていかれるのがいちばん困ります。
この形式をとるのは、Copilot は「聞いて分かったつもり」になりやすい道具だからです。説明を聞けば簡単そうに思えますが、実際に自分で打ってみると「提案が出ない」「思ったのと違うコードが出る」といったことが必ず起きます。その最初のつまずきを、教員がいる場で済ませてしまうのが狙いです。
① 基本インライン補完 － コメントを書いて Tab

最もよく使う機能です。コメントで「何をしたいか」を日本語で書いて改行すると、その下にコードが提案されます。Tab で採用、Esc で却下、Alt + ] で別の候補を表示。この演習ではこれが主戦力になります。

② 基本インラインチャット － Ctrl + I

コードを選択した状態で Ctrl + I（Mac は Cmd + I）を押すと、その場で日本語の指示が出せます。「このコードにエラー処理を追加して」「この関数を読みやすく書き直して」のように使います。

③ 対話Copilot Chat － サイドバーで会話する

サイドバーを開いて、日本語で AI と会話しながら進める使い方です。ふつうに質問してもよいのですが、先頭に決まった記号を付けると、AI に「何をしてほしいか」が正確に伝わり、返ってくる答えの質が大きく上がります。この演習では次の4つを覚えてください。

/explain最重要コードの意味を説明させる

何をするエディタでコードを選択してから /explain と入力すると、そのコードが何をしているかを日本語で説明してくれます。1行ずつの動作だけでなく、使われている文法の名前、なぜその書き方をするのか、どんなときに壊れるのかまで聞き出せます。

使う場面Copilot の提案を採用したものの、中身が分からないとき。班の他のメンバーが書いた部分を読むとき。授業で習っていない書き方に出会ったとき。

入力例（コードを選択した状態で） /explain 初心者にも分かるように、1行ずつ日本語で説明して /explain この書き方をする理由は？もっと簡単な書き方はある？

重要この演習の鉄則「説明できないコードを残さない」を守るための、いちばん現実的な手段です。意味の分からないコードを見つけたら、その場で投げる。これを習慣にできるかどうかで、4週間後の到達点が変わります。

/fixエラー対応原因を推測して直させる

何をするエラーが出ているコードを選択して /fix と打つと、原因の推測と修正案を出してくれます。修正後のコードは元との差分で提示されるので、どこがどう変わったのかを確認したうえで採用できます。

使う場面実行してエラーが出たが、エラーメッセージの意味が分からないとき。エラーは出ないのに、期待した結果にならないとき。

入力例（エラー箇所を選択し、エラーメッセージを全文コピーして貼り付ける） /fix 実行するとこのエラーが出ます：〔ここにエラー全文を貼る〕

コツエラーメッセージは省略せず全部貼ること。「なんかエラーが出ます」だけでは、AI も推測しかできません。逆に全文を貼れば、的中率は一気に上がります。

注意提示された修正が正しいとは限りません。採用する前に「なぜそれで直るのか」を /explain で確認してください。原因を理解しないまま直すと、同じエラーを何度も繰り返します。

/tests検証テストコードを書かせる

何をする選択した関数に対するテストコード（その関数が正しく動くかを自動で確かめるプログラム）を生成します。ふつうの入力だけでなく、データが空のとき・0のとき・想定外の値が来たときといった「境界のケース」も作ってくれることが多いのが利点です。

使う場面自分の書いた関数が本当に正しいか確かめたいとき。とくに AI が生成したコードを検証したいときに有効です。

入力例（関数を選択した状態で） /tests 境界値のケースも含めてテストを作って /tests 空のリストが渡されたときの動作もテストして

なぜ重要かAI の出したコードを AI に検証させるのは万能ではありませんが、自分では思いつかなかったケースに気づけるという効果があります。テストが通らなければ、そのコードはどこかが間違っています。「動いたように見える」で先に進まないための保険です。

@workspace範囲指定プロジェクト全体を見て答えさせる

何をするこれだけは他の3つと性質が違い、命令ではなく「見る範囲の指定」です。質問の先頭に付けると、いま開いている1つのファイルだけでなく、プロジェクトの中のファイル全部を見たうえで答えてくれます。

使う場面ファイルが増えてきて「あの処理、どこに書いたっけ」となったとき。班のメンバーが書いた部分も含めて全体像を知りたいとき。新しい機能をどのファイルに足すべきか相談したいとき。

入力例（コードの選択は不要） @workspace ログイン処理はどのファイルに書かれている？ @workspace この機能を追加するなら、どのファイルを直すべき？ @workspace このプロジェクト全体の構成を初心者向けに説明して

注意見る範囲が広いぶん、答えが返るまで時間がかかります。1つのファイルを見れば済む質問には付けないようにしてください。

④ 自動Agent（エージェント）モード － まとめて任せる

Chat の上部でモードを Agent に切り替えると、ファイルの作成・複数ファイルの同時編集・コマンド実行までまとめて自動でやってくれます。非常に強力ですが、その分何をされたか把握しにくく、後で自分のコードが分からなくなる原因にもなります。使うときは必ず差分を確認してください。

★ ③と④は「プレミアムリクエスト」を消費します。無料枠では月50回しか使えません（①と②の補完は月2,000回で実質使い放題）。詳しくは STEP 4 で説明します。Agent モードを気軽に回していると、2回目の演習日で枯れます。

これは、このマニュアルの「はじめに2」で挙げる落とし穴①──「動かないコードより、動くけれど間違っているコードのほうが危険」──とまったく同じことです。世界中のプロが、いま全員そこで困っています。

つまり現場が求めているのは 「AI を使える人」ではなく「AI の出力を検証できる人」です。前者は誰でも数分でなれます。後者になるには訓練が要ります。この演習で訓練するのは、後者です。

この4週間で、実際にこういう場面が来る

抽象的な話ではありません。以下は、この演習でほぼ確実に起きる場面です。

場面 1使ったことのないライブラリを使うことになる

状況「お店の位置を地図に表示したい」。地図を出すには専用のライブラリが必要だが、班の誰も触ったことがない。

従来英語の公式ドキュメントを読み、サンプルを探し、動かない原因を調べる。ここだけで半日から1日が消えます。

Copilot「地図を表示して、指定した緯度経度にピンを立てるコードを書いて」と頼めば、動く土台が数分で出ます。あとは自分たちのデータに合わせて直すだけ。

意味この演習は授業時間が合計20時間しかありません。この差は致命的です。Copilot を使う本当の狙いは、「調べる時間」を「何を作るか考える時間」と「ユーザーに聞きに行く時間」に振り替えることにあります。

場面 2公開したら動かない

状況自分のパソコンでは動くのに、インターネットに公開したら画面が真っ白。原因が分からないまま1時間が経過。

やることエラーログを全文コピーして /fix に貼る。

結果「設定ファイルの値が読み込まれていない」といった原因が、数十秒で指摘されます。

意味1回の授業は5時間弱です。この種の詰まりで2時間溶かすと、その週の実装は終わりません。調べ物の速度が、そのまま成果物の完成度に直結します。

場面 3班のメンバーが書いたコードが読めない

状況2週目、他のメンバーが書いた画面を自分が修正することになった。150行あって、どこから読めばいいのか分からない。

やること全部選択して /explain 全体の構造を初心者向けに説明して。

結果5分で全体像がつかめ、直すべき箇所が特定できます。

意味チーム開発でいちばん時間を食うのは、実は「他人のコードを読む時間」です。ここが速くなると、班の中で担当を融通できるようになり、1人が詰まっても全体が止まらなくなります。

場面 4使ってもらった人の指摘を、その場で直す

状況3週目、実際に触ってもらったら「ボタンが小さくて押せない」「文字が読めない」と言われた。

やることその場で修正して、次の人にもう一度試してもらう。

意味この演習の肝は「作って終わり」ではなく、「言われたことを直して、もう一度試してもらう」往復にあります。修正が速いほど、この往復を多く回せます。Copilot は、往復の回数を増やすための道具だと考えてください。

逆に、こう使うと失敗する

以下は毎年実際に起きている失敗です。先に知っておいてください。

✗ 失敗例1：Agent モードに丸投げする
「社会課題を解決するアプリを作って」と頼む → 15個のファイルが自動生成される → 一見それらしく動く → 1か所直したら全体が壊れる → 誰も直せない → 最初からやり直し。

3週目にこれをやると、まず間に合いません。速く進んでいるように見えて、いちばん遠回りです。
→ 正しくは：機能を1つずつ、自分が読める大きさで頼む。生成された差分は必ず目を通す。
✗ 失敗例2：/fix を連打する
エラーが出る → /fix → 別のエラーが出る → /fix → また別のエラー…… これを30分繰り返し、最初より状況が悪化する。

原因を理解しないまま直しているので、当然こうなります。
→ 正しくは：1回目の /fix の結果を /explain で確認してから採用する。「なぜそれで直るのか」が言えない修正は、採用してはいけません。
✗ 失敗例3：とりあえず Tab を押し続ける
提案が出るたびに内容を読まず採用 → 2週目には自分のコードなのに何が書いてあるか分からない状態になる → 修正できず、機能を足せなくなる。

→ 正しくは：読んで分からない提案が出たら、その場で /explain。ここを面倒がった班は、例外なく後半で止まります。

この演習で身につけてほしい3つの力

① 伝える力

  • AI に渡っているのは文脈だけ（図2）
  • 曖昧な指示には曖昧な答えが返る
  • コメント・変数名・頼み方を磨く

② 疑う力

  • 「ほぼ正しい」を見抜く
  • 世界中のプロの66%が困っているのがここ
  • テストを書いて確かめる習慣

③ 説明する力

  • 自分のコードを1行残らず説明できる
  • 班の他の人に引き継げる
  • この演習の評価軸そのもの
まとめると。この演習は「Copilot の使い方講座」ではありません。AI を道具として制御する側に立つ訓練です。制御される側になると、開発はむしろ遅くなります──失敗例1〜3が、まさにそれです。4週間後に「AI に書かせたけれど、全部説明できる」状態になっていれば成功だと考えてください。

得意・苦手と、使うときの心得

Copilot は万能ではありません。何が得意で何が苦手かを知らないまま使うと、かえって時間を溶かします。また、初めて使う人が必ずと言っていいほどハマる落とし穴が4つあります。事前に知っておいてください。

得意なこと・苦手なこと

得意なこと（どんどん任せてよい）苦手なこと（自分でやるべき）
定型的なコード（ループ、入出力、データ変換、画面の枠組み） 「何を作るべきか」の判断。これは人間の仕事です
初めて使う言語やライブラリの書き方を教えてもらう プロジェクト全体の設計。部分は書けても全体は組めません
エラーメッセージの意味を調べる（貼り付けて聞くだけ） ごく最近出たライブラリ。学習データに含まれていません
既存コードが何をしているかの説明（/explain） 正しさの保証。動くコードと正しいコードは別物です
テストコードやサンプルデータの生成 あなたの意図の推測。曖昧な指示には曖昧な答えが返ります
コメント・ドキュメント・コミットメッセージを書く 複雑な業務ルールや、その場限りの特殊な仕様の実装

初めて使う人が必ずハマる4つの落とし穴

① 平気で間違えます。しかも自信満々に。
存在しない関数を呼び出す、引数の順番が違う、境界の条件（0のとき、空のとき、最後の1件）を間違える──こういうことが日常的に起こります。これは不具合ではなく、仕組み上そういうものです。
そしていちばん危険なのは「動かないコード」ではなく「動くけれど間違っているコード」です。動かなければすぐ気づきますが、動いてしまうと最後まで気づきません。提案されたコードは必ず自分で読んでください。
★ ② 何も考えずに Tab を押し続けると、力がつきません。
これは実際に毎年起こります。「動いたからヨシ」で進むと、2週目に必ず詰みます。自分のコードなのに、どこを直せばいいのか分からなくなるからです。
対策は簡単で、意味の分からないコードを見たらすぐ /explain に投げる、それだけです。習慣にしてください。
③ 入力してはいけないものがあります。
入力した内容はクラウド上の AI に送信されます。次のものは絶対に書かない・貼らないでください。
・API キー、パスワード、アクセストークン　・自分や他人の個人情報　・他人の未公開のコードや、公開が許されていない資料
特に API キーをコードに直接書いて GitHub にアップロードするのは典型的な事故です。演習中も必ず守ってください。
④ AI の利用ルールは、授業ごとに違います。

1-1　アカウントを作る

  1. https://github.com/ にアクセスし、Sign up をクリック。
  2. ユーザー名は今後もずっと使えるものにしてください（就職活動でも使います）。
  3. すでにアカウントを持っている人は 1-2 へ進んでください。

1-2　大学のメールアドレスを登録・認証する

学生認証で最も重視される項目です。

  1. 右上のアイコン → Settings → 左メニューの Emails。
  2. Add email address で大学のメールアドレスを追加。
  3. そのアドレス宛に届く確認メールのリンクをクリックする。

1-3　プロフィールを埋める

★ 空のプロフィールは審査で落ちる原因になります。「アカウントを作っただけ」の状態では通りません。
  1. Settings → Public profile。
  2. Name：本名をアルファベット表記で（例：Taro Yamada）。学生証の氏名と一致させてください。
  3. Bio：一言でよいので入れる（例：Student at Doshisha University, studying information systems.）。
  4. アイコン画像も設定しておくと通りやすくなります。
⚠ 先に知っておくこと：GitHub のプロフィールは全世界に公開されます。
Name 欄に入れた名前は、大学とは無関係の誰からも見られます（検索エンジンにも載ります）。氏名を公開したくない場合は、下の選択肢を読んでから決めてください。

なお 本名の登録は、学生認証の「必須条件」ではありません。審査で本当に必要なのは学生証の画像と大学メールです。本名を入れると通りやすくなる、という経験則があるだけです。
案 A審査の間だけ本名にして、通ったら変える（おすすめ）

申請時は本名を入れて審査に通し、承認メールが届いたら Name を好きな表記に変更する方法です。承認後の変更は自由で、資格が取り消されることはありません。審査通過率とプライバシーの両方を取れるので、迷ったらこれを選んでください。

案 B最初から本名を入れない

Name 欄は空欄またはニックネームのままにし、Bio とアイコンだけ埋めて申請します。それでも通ることは多いです。もし却下されたら、そのとき本名を入れて再申請してください。却下されても不利益はありませんので、この順番でも構いません。

案 C本名のまま運用する

GitHub のアカウントはそのまま就職活動のポートフォリオとして使えます。「何を作れる人なのか」を本名で示せることには実際に価値があり、意図して本名で運用している技術者は大勢います。将来そう使うつもりなら、この選択も十分に合理的です。

どれを選んでも構いませんが、次の項目（1-5）だけは全員必ず実施してください。名前を隠しても、メールアドレスが漏れていては意味がないためです。

1-4　二段階認証（2FA）を設定する

  1. Settings → Password and authentication。
  2. Two-factor authentication を有効化。
  3. スマホに認証アプリ（Microsoft Authenticator / Google Authenticator など）を入れて設定。
⚠ リカバリコードを必ず保存してください。
スマホを機種変更・紛失すると、リカバリコードがない限りアカウントに二度と入れなくなります。表示されたコードをスクリーンショットし、クラウドと紙の両方に残してください。毎年これで詰む人がいます。

1-5　メールアドレスを非公開にする（全員必須）

⚠ 何もしないと、あなたのメールアドレスが全世界に公開されます。
Git は、コミット（保存）のたびに作業者のメールアドレスをコードの履歴に埋め込みます。公開リポジトリなら、その履歴は誰でも読めます。つまりふつうに設定すると、大学のメールアドレスが誰でも取り出せる状態になります。スパムやフィッシングの標的になるので、必ず対策してください。
対策は簡単です。GitHub が身代わりのアドレス（noreply アドレス）を用意してくれているので、それを使います。
  1. https://github.com/settings/emails にアクセス。
  2. Keep my email addresses private にチェックを入れる。
    → メールアドレスが非公開になり、その下に 1234567+ユーザー名@users.noreply.github.com という形式のアドレスが表示されます。
  3. Block command line pushes that expose my email にも必ずチェックを入れる。
    → こちらは保険です。万一 STEP 3 の設定を忘れても、GitHub 側がアップロードを拒否してくれるので事故を防げます。
  4. 表示された noreply アドレスをコピーして控えておく。STEP 3 で使います。
ここで確認　チェックボックスが2か所ともオンになっていること。そして @users.noreply.github.com で終わるアドレスが画面に表示されていること。このアドレスは人によって違います（先頭の数字はあなた専用の ID です）。
補足：この設定をしても、GitHub からの通知メールは今までどおり自分のアドレスに届きます。「他人から見えなくなる」だけで、不便になることはありません。
